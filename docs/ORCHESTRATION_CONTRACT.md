# Director execution candidate

The deterministic Director uses the existing private SQLite store, JD-04 executor and FIFO queue. It does not replace Hermes reasoning/chat. One authorized Owner task produces Developer → QA → at most one self-fix → committed candidate → durable checkpoint → report outbox. Each stage submits asynchronously and polls on later ticks. There is no merge/deploy stage.

`POST /api/projects/{id}/runs` accepts `task_id`, `approval_ref`, `idempotency_key`. The principal needs `read`, `workflow:run`, `workflow:director`, `workflow:developer`, `workflow:qa`, `engineering:execute`, `engineering:read`. Project config must name `repository`, a non-main `branch`, `environment: isolated-development` and `pipeline: {developer, qa, self_fix}` with project-scoped command profiles. Developer/self-fix profiles require `role: developer`, `executor: codex`; QA requires `role: qa`, `executor: local-ci`. Owner approval is rechecked before each tick and must not expire. Director mandates additionally bind `repository`, `branch`, `environment`, `owner_actor`, `max_cost_usd: 0`, `allowed_actions` including `engineering:execute` and `qa:execute`, and `forbidden_actions` including `merge`, `production:deploy`, `paid-api`, `other-repository:write`. A missing or mismatched field denies execution. Auth-file updates require an integrating host reload; this candidate does not continuously watch the private file. An already queued/running command is not revoked atomically by the Director; host admission/revocation enforcement remains a live release gate. These config records are private and never committed.

Exact stage instructions are persisted before enqueue and reused across restart so changed worktree content cannot change idempotent command input.

A fixed argv profile may contain the exact argument `{workforce_instruction}`. The private bridge replaces this with ONE bounded JSON argument containing task instruction, project/run/task IDs, stage, attempt and candidate SHA; no shell or arbitrary argv is accepted. A reviewed Codex/Local CI wrapper must consume that JSON and enforce the mandate. No wrapper is installed into Hermes by this change. Conversation fallback models never receive this instruction or engineering tools.

QA exit code zero plus a clean Git snapshot on the configured repository/branch produces acceptance evidence. SHA before/after QA must match. This is fixed-profile executor evidence, not an independent assertion that the QA command is comprehensive. Pipeline profiles must be reviewed. Native Hermes approval remains mandatory at the host boundary; backend ACL configuration is not proof of a native human approval. The plugin shim uses the actual native request API and fails closed on pending/deny.

`GET /api/projects/{id}/runs` lists subject-owned runs. The Director scheduler is opt-in via `createApp({startDirector:true})`; default is OFF and no Gateway/service is started. Host code can call `director.tick()` or `director.start()` after acceptance. Interrupted/cancelled execution blocks without replay. `POST /api/projects/{id}/runs/{run}/resume` additionally requires recovery scope/approval, explicit side-effect reconciliation and a bounded note. Notes enter audit only as hashes. A new execution generation avoids reusing the old job key; maximum two reviewed recoveries.

Release and blocker/critical-approval reports share the durable outbox, with distinct delivery keys across reviewed recoveries. No approval is granted through the outbox.

Outbox delivery is prepared through `director.deliverReports(existingTransport)`. The injected existing Hermes/Jack transport implements `send(payload) -> {acknowledged:true}` and deduplicates `delivery_key`. It must bind the original authenticated Owner/project routing; no raw logs/prompts/credentials in payloads. No bot/API credential is created. A crash between send and acknowledgement can retry delivery. Current `REPORTED` means locally checkpointed and report queued; it does not mean Telegram received it. Check `report_outbox.delivered_at` for acknowledgement. Pending approvals remain native; no approval mutation endpoint is added.

No worker delegation, real Codex coding, live Telegram delivery or runtime autonomy is claimed by the synthetic acceptance suite.
